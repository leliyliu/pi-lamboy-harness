# 通知链路诊断报告 — pi 会话结束/error 不弹提醒

**日期**：2026-10-12（v3 修复日）
**结论**：不是 Paseo 损坏，也不是 pi 配置错误——是**通知职责空档**。v1/v2 均实测不可行，v3 改走 /dev/tty OSC + kitty 作为通知宿主，待重启实测；paseo-notifier 评估结论：仅对 Paseo-daemon 内 agent 有效，对 kitty 直跑会话不可见。

---

## 1. 症状

pi 会话 turn 结束或 error 后，不再有弹窗提醒。用户疑问：是 Paseo 的影响，还是 pi 配置问题。

### 2.3 结论推导

- **"turn 结束弹窗"从未完整存在过**：Paseo 无完成类通知（事实 1）；kitty 链路缺弹窗组件（事实 8-10）。
- **"error 弹窗"**：Paseo 明确 error 不推系统（事实 2）；kitty 链路弹窗组件缺失（事实 10）。
- 以前感知到的"提醒"实际来源：Paseo 内跑时的 permission 弹窗（离场时）、或 focus-bell 铃声/tab 标记。
- Paseo.app.old 残留说明升级过，但日志显示主因是**会话不经 Paseo**（事实 4），非版本回归。

## 4. 验证记录

### v1（OSC 99 via process.stdout.write）— 不可行

用户实测反馈不可行。根因分析（两条，均有证据）：

1. **pi TUI render buffer 吞掉 stdout**：pi-focus-bell 源码注释明确写着 BEL 要 "written straight to the pane's slave tty ... **bypassing pi's TUI render buffer**"——TUI 模式下扩展直接 process.stdout.write 不可靠。
2. **kitty OSC 99 聚焦抑制**：kovidgoyal/kitty#6755 讨论“窗口聚焦时抑制桌面通知”，官方将其视为待完善的特性需求。

### v2（osascript 原生通知）— 实测不可行（2026-10-12 14:05 会话取证）

用户重启 pi 后新会话（14:05）实测：直接跑 `osascript -e 'display notification ... sound name "Glass"'` 返回 exit=0，**用户明确反馈“好像没看到弹窗和声音”**。

- 通道靜默失败：exit=0 只证明 AppleScript 进程跑完，不证明通知投递（上轮“已验证”系过度断言，已纠正）
- 权限表面正常：Script Editor ncprefs flags=8206 → enabled=1, style=3, sound=1（style=3 与 FaceTime/邮件/短信相同，为正常样式）
- 无 DND/Focus 生效（Assertions.json 不存在）
- 真实原因被 TCC 墙挡住，CLI 无法继续定位 → 结论：**放弃 osascript 作为主通道**

### v3（/dev/tty OSC + kitty 宿主）— 已部署待实测

设计：
- OSC 99（kitty）/ OSC 777（其他终端）直接写 `/dev/tty`：绕过 pi TUI 对 process.stdout 的接管（focus-bell 同款做法，其 BEL 就是这么响的）
- 通知宿主 = kitty：首次触发后 kitty 出现在 系统设置→通知，权限肉眼可见可控
- /dev/tty 不可写时回退 osascript；headless（ctx.mode!="tui"）静默
- 调试日志 `/tmp/pi-notify.log`（PI_NOTIFY_DEBUG 覆盖路径）：settled 触发、mode、body、tty 写结果全记录
- PI_NOTIFY=0 完全禁用

验证：esbuild ✅ / headless 加载 ✅（无副作用，无日志，符合 TUI-only 预期）/ TUI 实测 ⏳ 待用户重启后观察

实测方法：重启 pi → 跑任意 turn → 应弹「✅ Ready for input」；若仍不弹，查 `cat /tmp/pi-notify.log` 看 `ttyWrite=` 值，并查 系统设置→通知→kitty 是否出现且允许。

## 7. 最终定案（2026-10-12 第三轮，用户确认日常宿主为 Paseo 内嵌终端）

### 根因收束

进程链实证（bash ← pi ← zsh ← Paseo Helper ← Paseo Daemon）：用户日常 pi 会话跑在 Paseo 内嵌终端（xterm.js），不在 kitty（TERM_PROGRAM=kitty 系环境变量继承假象；KITTY_WINDOW_ID 为空）。因此：

- v1/v3 的 OSC 99/777 到达 xterm.js 后被静默丢弃（xterm.js 不处理桌面通知协议）
- v2 osascript：Finder/SystemEvents 宿主对照实测全部不可见（用户确认 A/B 均未到达），macOS 15.5 + JD 企业环境下 osascript 全宿主阵亡；terminal-notifier 也被拒（Notifications are not allowed for this application）
- MDM 排除：profiles 仅 JD 证书（UserCAv1.1 / CA Certificate），无通知压制策略

### 关键考古

`~/.paseo/agents/` 7 条 provider=pi 的 agent 记录，创建于 9/13–9/20，attentionReason 字段佐证：**用户原工作流 = Paseo agent 模式跑 pi，通知正常**；9/20 后改为内嵌终端手敲 pi（daemon agents.total=0，零追踪、零通知）。

### Paseo 原生通知体系调查结论

- 通知是 **agent 维度**：attention(permission/error/finished) + 180s presence 策略（在场→应用内横幅；离场→Electron 系统推送）。sh.paseo.desktop 在 ncprefs 注册 enabled=1 style=3 sound=1，且 9 月中旬实际工作过
- 终端维度只有：zsh shell integration（OSC 633 A/B/C/D，preexec/precmd 钩子）→ commandFinished 事件仅5处消费者（runtime 生命周期 + IPC 转发），**无 GUI 通知消费**；terminal activity attention 仅 tab 标记级
- error 类 attention 不发系统推送（isPushEligibleAttentionReason = reason !== "error"）——agent 模式下 error 提醒是应用内横幅

### 最终方案

**pi 交互会话回 Paseo agent 模式**（GUI composer 或 `paseo run -d`）：daemon 全程追踪，完成时离场即系统推送；pi 全局配置/扩展/AGENTS.md 照常加载（daemon 驱动同一 pi 安装，PiCliRuntime 继承 globalConfigPath）。内嵌终端保留给 shell 工作。v1-v3 的 ~/.pi/agent/extensions/notify.ts 已删除，环境清理完毕。

验收：`paseo run -d` 已实测 daemon 追踪正常（7766a23/a2692153 均跑完）；系统推送需用户离场 ≥180s 后自然触发。

### “以前会弹”的真相

9/13–9/20 用户在 Paseo agent 模式跑 pi，看到的是 **Paseo in-app 红点/横幅**（应用内 UI），非系统推送——系统推送在这台机器上从未对 Paseo 工作过（ncprefs 记录从未在系统设置列表显示 = 从未授权成功）。

### 429 error 场景说明

- Paseo 设计上 error 类 attention 不发系统推送（isPushEligibleAttentionReason = reason !== "error"），只发应用内横幅——即使授权修通，429 error 也不会有系统弹窗
- pi 侧 40-goal.ts 已有 429 自动恢复（usage_limited → provider 恢复时自动 resume）
- 429/离座/error 的可靠提醒 = 声音（Basso）+ 手机推送（paseo-notifier）

## 10. v5 终案（2026-10-22 第五轮）：绕开通知中心，自绘浮窗

### 症状复述（用户反馈）

> 之前说在 paseo 中运行 pi agents，想要提醒……现在完成之后似乎会有声音提醒，但没有弹窗提醒，我想补充上这个。

与 v4 部署一致：afplay 出声、弹窗无。

### 新证据（本轮实测）

| 检测项 | 命令 | 结果 |
|---|---|---|
| 通知授权 | `pinotif "..." "..."` | `granted=false err=UNErrorDomain Code=1 "Notifications are not allowed for this application"` —— 系统已重启（usernoted 今日 10:09 启动）仍未解锁，**策略层封锁未变** |
| 系统通知库 | `plutil -p ~/Library/Preferences/com.apple.ncprefs.plist` | `com.liulian.pinotif` 有记录，但允许位未置 |
| `display notification` | v4 日志 `/tmp/pi-notify.log` | **`osascript exit=0` 却无弹窗** —— 假成功，此前日志因此误判通道健康 |
| `display dialog` | `osascript -e 'display dialog "..." giving up after 5'` | **真实弹出**（返回 `button returned:好`），属脚本自身 UI，不经通知中心 |

**根因补充**：`display notification` 投递被拦时仍返回 exit 0，退出码无法判定通道死活——这解释了「日志全绿、屏幕没弹窗」。

### 方案：自绘 NSPanel 浮窗（不经 UNUserNotificationCenter）

新工具 `pinotify`（Swift + AppKit，源码 `personal/notify/pinotify.swift`，构建脚本 `personal/notify/build.sh` → `~/.pi/agent/bin/pinotify`）：

- `NSPanel` + `.borderless` + `.nonactivatingPanel` + `.ignoresMouseEvents`：**不抢键盘焦点、鼠标穿透**
- `level = .statusBar`（窗口 layer 25）+ `collectionBehavior = [.canJoinAllSpaces, .fullScreenAuxiliary, .stationary]`
- `NSVisualEffectView` 毛玻璃卡片：右上角滑入 → 停留 6s → 淡出退出
- 多实例槽位 `/tmp/pinotify-slots/<slot>.pid`：`kill(pid,0)` 探活清理僵尸槽位，最多 6 个纵向槽位，避免多 agent 同时结束叠窗
- 不申请任何 TCC / 通知授权——纯本进程画自己的窗口

### 客观验证（不靠肉眼）

`CGWindowListCopyWindowInfo` 过滤 348×88 窗口：

```
MATCH owner=pinotify layer=25 x=1558.0 y=137.0 w=348.0 h=88.0   ← error 浮窗
MATCH owner=pinotify layer=25 x=1558.0 y=39.0  w=348.0 h=88.0   ← success 浮窗
```

两实例同时存在且 y 错开（39 / 137），槽位互斥生效；屏幕宽 1920，`1558+348+14=1920` 贴右上角。

端到端（jiti 加载 `notify.ts` + mock `ExtensionAPI`，触发 success / error）：

```
[log] settled mode=tui aborted=false err=false
[log] pinotify spawned kind=success
[log] settled mode=tui aborted=false err=true
[log] pinotify spawned kind=error
[log] afplay Glass exit=0
[log] afplay Basso exit=0
```

### notify.ts v5 通道链（fail-open 逐级回落）

1. `pinotify` 浮窗（主通道）—— 缺失或 `spawn` error 时回落
2. `osascript display dialog ... giving up after 5`（回落）—— 已实测可用，缺点是模态、抢焦点
3. 仅 `afplay` 声音 + 日志

已移除 `display notification`（假成功，无诊断价值）。文案携带项目名（`ctx.cwd` basename）与耗时，便于 Paseo 多 agent 并行时辨认。

### Paseo 环境确认

当前 pi 进程链 `Paseo Supervisor → Paseo Daemon → Paseo Helper → zsh → pi`，`launchctl managername = Aqua` → 具备 WindowServer 连接 → 浮窗在 Paseo 内嵌终端跑的 pi 中同样可见。

### 生效方式

扩展在 pi 启动时加载：新会话自动生效；当前会话执行 `/reload` 生效。
